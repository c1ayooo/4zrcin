# 20 规则热更新：实例规则与节点就地生效（实施文档）

状态：**已实施**（2026-11-28），改动在四条车道里：引擎、外壳、4zweb、4zgears 各一条 `feat/rules-hot-reload`，都在 `~/wt/rules/` 下，四条都已提交。4zgears 的那条已推送，两个仓钉的是它的版本号，见 §6。它让操作员在控制台里看到节点实际在跑的指纹与 POC，录入实例规则，并让运行中的本地节点在下一次工具调用时就用上，不重启、不重编、不分发；新增、改写、删除都一样。设计取向见 [agent.md](../agent.md)，现行架构见 [docs/01](01-architecture.md)，规则仓与编译期链路见 [docs/19](19-decoupling-plan.md) §5，资源分层的预留方向见 [docs/04](04-templates-and-resources.md) §6。文中的路径与函数名取自实施时的检出，只用于定位，不是契约。

## 0. 目标与边界

规则分两层。**内置规则**来自规则仓 `4z/rules`，由引擎生成器编进 scan，改它要重跑生成、重编、分发。**实例规则**是数据目录里的文件，归这个实例所有。节点上有一块积木盯着实例目录，目录变了就把运行中的引擎改成目录说的样子，所以改实例规则不碰节点。

交付：

- 规则库页面列出节点实际在跑的指纹与 POC，内置与实例都在，正文能看。
- 控制台录入、改写、删除实例规则，按路径导入保留。
- 新增、改写、删除在本地节点的下一次工具调用时生效，不重启。
- 实例规则可以覆盖同名的内置指纹或同 `id` 的内置 POC；实例文件删除后内置的那条回来。
- 改写被节点拒绝时，节点继续运行上一版，页面显示原因。
- 每条规则的节点状态如实显示：已生效、等节点空闲、失败及原因。

不在范围：

- 远程节点。它们读不到控制面的目录，要另走下发通道（docs/04 §6 的第三层）。
- 字典、zombie 规则、端口表。它们没有运行时接口。
- 改写内置规则本身。仍然走规则仓。

## 2. 已核实事实（构成约束）

**引擎（cyber-harness）**

1. 资源集只在启动时构建一次：`exts/scanner` 的 `Load` 调 `engine.InitWithOptions`（`tools/scan/engine/set.go`）。指纹只有内嵌和 cyberhub 远端两个来源，POC 多一个每次调用的 `-t`。
2. 工具每次调用都现读引擎：`tools/scan/adapter.go` 每次从引擎集取；`neutron` 的选择读 `engine.Get()`（`tools/neutron/sdk_stage.go`）。引擎变了，下一次调用就是新的。
3. `-t` 是替换：给了就只跑这些模板，内置的不参与（`tools/neutron/neutron.go`）。
4. 任务钩子是成对的：`tool.started` 在准入之后发，`tool.completed` 在 defer 里发并覆盖所有出口，含 panic（`core/tool/hooks/execute.go`）。被拒的任务只发完成通知。两个钩子点都不向任务返回错误。
5. `extension.Provide` 不接受空值；`Use` 借不到就加载失败（`core/extension/scope.go`、`core/resource/resource.go`）。
6. 资源包的空孪生与 `emptyresources` 标签已删除（引擎 `1ba7bbd5`，2026-11-28）。任何运行模式下规则都编在 scan 里，所以改内置规则只能重编。
7. 架构测试不禁止积木 import `tools/scan/engine`，它只规定谁可以调用登记在册的安装符号（`InitWithOptions` 只属于 `exts/scanner`）。积木不调用它。

**选择过程**

8. `scan` 流水线先用指纹识别目标，再拿识别出的指纹查关联索引，索引给出该跑哪些 POC（`tools/scan/engine/neutron.go`）。关联按 POC 的 `finger` 字段建，字段名是 `finger`，值是列表（`sdk/pkg/association/index.go`、neutron 的 `Template`）。每个指纹最多选 20 条。
9. 内嵌的 83 条 POC 没有一条写 `finger`，也没有一条带 CPE。所以 `scan` 默认一条内置 POC 都不跑，只有 `--broad-poc` 才跑。实例 POC 写了 `finger` 就一定被选，排在所有内置之前。
10. 直接调 `neutron` 时不加筛选：写了 `finger` 的 POC 被跳过，免得在没有指纹证据时误报；没写的全跑。

**4zgears**（sdk 的 fork，模块路径仍是 `github.com/chainreactors/sdk`；`dcad8620f5e9` 加本次改动）

11. `neutron.Engine.AddPocs` 把新模板编译后追加进 `e.templates`；编译不过的被丢弃，只有全部失败才报错。原来没有移除的方法。
12. `fingers.Engine.AddFingers` 把指纹追加进当前实现，并按 name 并入配置；`Reload` 按配置原地重建。原来没有移除的方法。
13. 底层的 `Append` 不去重，所以改写一条指纹要 `AddFingers` 之后再 `Reload`。
14. 指纹与 POC 的关联索引带读写锁，`BuildWithFingers` 原地重建。
15. gogo 与 spray 两个引擎都只持有指纹引擎的指针，运行时才取当前实现（`sdk/gogo/gogo.go`、`sdk/spray/spray.go`）。
16. 文件加载器：指纹文件是 YAML 列表，POC 文件是单个文档或列表（`sdk/pkg/provider/file.go`）。只有 `id` 和 `info` 的模板编译不过，POC 必须带请求块。
17. gogo 的扫描任务由主机和端口两个参数组成。
18. `Template.Compile` 会往请求列表里追加（neutron 的 `templates/impl.go`），所以它不是幂等的。
19. 匹配结果里的键是显示名：引擎会把名字转小写，个别已知产品会换个写法（`dnp-firewall` 的结果是 `dnp firewall`）。

**外壳（4zrcin）**

20. POC 库曾是 `<data>/pocs` 一个目录（`internal/pocs`），接口只有列表和按路径导入。指纹没有入口。
21. `pocDir()` 只要库非空就把它写进任务书。
22. 本地节点的环境变量在 `internal/host` 的 `childEnv` 里按需追加。
23. `internal/kb` 已有两层库的写法：实例条目覆盖内置同名条目、原子写、带修订号的删除。
24. 路由有四张表必须同步；实例级写接口对 agent 隐藏（`cmd/zrcin/route_matrix_test.go`、`agent_surface_test.go`）。

## 3. 用户故事

1. 作为操作员，我希望在规则库里看到节点内置的全部指纹与 POC，以便知道执行者手里有什么。
2. 作为操作员，我希望点开一条规则能看正文，以便判断它为什么会命中或不命中。
3. 作为操作员，我希望在页面里直接粘贴一条 POC 或指纹，以便不用登录机器去改文件。
4. 作为操作员，我希望新增的规则不用重启节点就能用上，以便不打断正在跑的意图。
5. 作为操作员，我希望改写一条 POC 后下一次调用就跑新的，以便在同一个意图里接着验证。
6. 作为操作员，我希望删掉一条规则后它马上不再运行，以便停掉一条误报的规则。
7. 作为操作员，我希望每条规则显示节点是否已生效，以便不把「存进去了」当成「在跑了」。
8. 作为操作员，我希望规则写错时看到节点给的失败原因，并且原来那条还在跑，以便一个笔误不会让规则停摆。
9. 作为操作员，我希望扫描进行中改规则时页面说「等节点空闲」，以便知道它稍后会生效，而不是丢了。
10. 作为操作员，我希望把一条内置规则另存为实例规则再改，删除后内置的那条回来，以便不碰规则仓就能临时修一条。
11. 作为操作员，我直接往目录里放文件或改文件时，希望节点同样接住，以便沿用现有的工作习惯。
12. 作为操作员，我希望新建 POC 时看到 `finger` 字段和它的作用，以便新增的 POC 能被 `scan` 选中。
13. 作为操作员，我希望按路径批量导入规则仓的检出，以便不重编就能用上一批新规则。
14. 作为执行者，我希望用 `cyberhub` 搜到节点刚加载的规则，以便在同一个会话里用上它们。
15. 作为操作员，我希望没配置规则目录的节点完全不受影响，以便远程节点照旧工作。

## 4. 总体设计

### 4.1 目录

```
<data>/rules/
  fingers/<分类>/*.yaml      YAML 列表，格式同规则仓的 fingers/http
  pocs/<id>.yaml             nuclei 风格的单个模板
  .node/                     节点回写，外壳只读
    builtin-fingers-http.json
    builtin-fingers-socket.json
    builtin-pocs.yaml
    state.json
```

- 写入单位是文件，寻址用相对路径。列表按规则展开：一个文件里的多条指纹各占一行，标出所在文件。
- 指纹的分类目录就是它的 tag，与生成器一致；文件里没写 tag 时由节点补上。从控制台录入的指纹默认放 `custom`。
- 实例规则与内置规则同名（指纹）或同 `id`（POC）时，实例的生效，页面标「覆盖内置」。实例文件删除后内置的那条回来。

### 4.2 下发

外壳启动本地节点时注入 `CYBER_RULES_DIR=<data>/rules`（`internal/host` 的 `withRulesDir`，进程内 Hub 和外部 Hub 两条启动路径都走它）。节点侧积木声明 `rules` 配置节，这个环境变量映射到它的 `dir`。没有配置时积木是空操作。

选环境变量而不是配置文件，原因同节点代理（`internal/settings/node_proxy.go` 的说明）：节点连上 Hub 之后，文件里的产品节不保证留得住，环境变量是外壳已经在用的送达方式。

### 4.3 节点积木 `exts/4zrules`

纯新增包。装配顺序在扫描器扩展之后，`Use[*engine.Set]` 借到运行中的引擎集。扫描器在引擎集建好后把它 `Provide` 出去，是这次唯一的上游文件改动（`exts/scanner/extension.go`，10 行，登记在引擎 `FORK.md`）；引擎初始化失败时给一个空集，节点照常启动。

**触发**有三处：每秒一次的定时检查；扫描类任务开始前；扫描类任务结束后。扫描类任务是 gogo、neutron、spray、scan 四个工具的调用。开始前的那次检查保证「下一次调用就用上」，定时检查让空闲节点的状态及时变成已生效。

**条件**：目录签名变了，且在跑的扫描类任务数为零。在跑的数量按调用 id 记：`tool.started` 记入，`tool.completed` 移除。不满足就标为待生效，等下一次触发。

**签名**：`fingers/` 与 `pocs/` 下全部 yaml 文件的相对路径、大小、修改时间。外壳写入时保证修改时间严格递增，排除同一时刻、同样大小的覆盖被漏掉。

**积木给每个文件记三样东西**：节点上次放进引擎的是什么（POC 的 `id` 列表或指纹的名字列表）、当时读到的正文、以及磁盘上那份的签名。

**步骤**（持锁）：

1. 逐个处理新增或有变化的文件。先把文件读出来解析，解析失败的不动引擎：
   - 变化了的文件：把上一版放进去的东西取出来，被它盖住的内置规则放回去。
   - 放进新版：同 `id` 的内置 POC 或同名的内置指纹让位，然后追加新内容。POC 由 `RemovePocs` 加 `AddPocs` 完成，只有新内容被编译；指纹由 `RemoveFingers` 加 `AddFingers`，最后统一 `Reload`。
   - 引擎拒绝了这个文件：上一版用它自己的正文重新解析后放回去，记为失败，原因后面注明节点仍在运行上一版。
2. 消失的文件：同第一步的「取出来」，然后不再有它的记录。
3. 有指纹变化就 `Reload`。
4. 原地重建关联索引。
5. 写 `state.json`，先写临时文件再改名。

启动时在第一次工具调用之前先做一次，所以重启后实例规则按磁盘现状全部加载。空库也要写状态文件：签名只在该应用过之后才参与比较，否则一个刚起的节点会被控制台读成「未上报」。

**恢复内置**：被覆盖的内置规则从节点回写的清单里重新解析出一份再加回去，不复用之前的对象，因为编译不是幂等的（R6）。

**回写**：加载时把节点启动时加载的规则集原样落成三个文件（引擎集 `Resources` 里的 `http`、`socket`、`neutron` 配置字节），每次应用后写 `state.json`。控制面只读这个目录。

### 4.4 控制面

`internal/rules` 取代 `internal/pocs`，写法照 `internal/kb`：

- 保存时做结构校验：POC 必须有 `id`，字符集同原来的 `sanitizeID`；指纹必须是列表，每项有 `name` 和 `rule`。能否编译由节点判定，结果回显。
- 原子写，修订号是正文摘要；改写和删除带上修订号，对不上返回 409。
- 列表是两层的合并：实例文件解析成行，内置清单解析成行，被实例覆盖的内置行不单列。节点状态文件里有记录、磁盘上已经没有的文件也列一行，带着节点上次说的状态。两边都按目录签名缓存，做法同原来的 `internal/pocs`。
- 每行 POC 带着它的 `finger` 字段，两层都带。
- 内置指纹的正文由节点回写的 JSON 转成 YAML 列表，空的 `Attributes` 字段去掉。
- 现有 `<data>/pocs` 里的文件：启动时若 `rules/pocs` 为空就复制过去并打日志（`rules.AdoptLegacyPOCs`），旧文件不动。

### 4.5 控制台

「POC 库」页改成「规则库」（`src/views/Rules.tsx`）：指纹与 POC 切换，来源筛选（全部、内置、本实例），搜索在服务端。每行显示来源、节点状态和是否覆盖内置。右栏看正文：实例规则可编辑，内置规则可「另存为本实例规则」。POC 的详情里写它绑定了哪些指纹；没绑定时说明 `scan` 不会自动选它。按路径导入保留，另加粘贴新增，新建 POC 时预填带 `finger` 字段的模板并注释它的作用。

列表不自己轮询。页面每 3 秒读一次节点状态，节点的上报时间变了才重新读列表。删除走确认对话框；一个指纹文件里有几条时，对话框会说明它们一起删。

### 4.6 与另外两条路的关系

- **cyberhub 通道**：引擎自带的启动时拉取，覆盖指纹和 POC，24 小时缓存，重启才生效。本方案不依赖它，也不改它；两者可以并存，远端拉来的规则算在内置清单里。
- **`neutron -t`**：不变。它是给「这一轮只跑这些模板」用的替换语义；实例规则走默认规则集，不再经任务书交给执行者。

## 5. 契约

### 5.1 配置

| 项 | 值 |
| --- | --- |
| 配置节 | `rules`，字段 `dir` |
| 环境变量 | `CYBER_RULES_DIR` |
| 未配置 | 积木空操作 |

### 5.2 节点回写

`state.json`：

```json
{
  "brick": 2,
  "updated_at": "2026-11-28T08:00:05Z",
  "available": true,
  "pending": false,
  "builtin": {"fingers": 4314, "pocs": 83},
  "files": [
    {"path": "pocs/e2e.yaml", "kind": "poc", "state": "applied", "parsed": 1, "compiled": 1},
    {"path": "pocs/broken.yaml", "kind": "poc", "state": "failed", "reason": "parse pocs/broken.yaml: yaml: unmarshal errors: …; the node keeps running the previous version"}
  ]
}
```

`files` 只列实例文件。`available` 为假时带 `reason`，例如节点没有扫描引擎；目录读不了时带 `error`。一条规则被拒绝时 `parsed` 和 `compiled` 描述的是仍在运行的上一版。

### 5.3 规则状态

| 状态 | 含义 | 页面文案 |
| --- | --- | --- |
| `applied` | 节点已加载当前内容 | 已生效 |
| `pending` | 内容变了，有扫描在跑 | 等节点空闲 |
| `failed` | 节点拒绝了当前内容；之前加载过的版本继续运行，原因里注明 | 失败，带原因 |
| 未上报 | 节点没启动，或不带这块积木 | 节点未上报 |

`failed` 的文件在内容变化之前不再重试，不会因为一个坏文件反复编译。

### 5.4 HTTP 接口

全部是实例级，对 agent 隐藏，路由矩阵与 agent 面测试同步。筛选用 `all` 表示不筛选。

| 方法 | 路径 | 请求 | 说明 |

| GET | `/api/rules` | `kind`、`source`、`q`、`offset`、`limit` | 合并列表与节点状态；`matched` 是过滤后的总数 |

## 7. 失败模式

| 上一版也放不回去（理论上不会，它编译过） | 日志里记一条，这一条不再运行 |

## 9. 测试与验收

**接缝**（能在最高处测就不往下开）：

- sdk：在包内直接构造引擎，测移除与改写。
- 引擎：引擎集 `engine.Set` 一处；积木用真实的 `hooks.Registry` 发 `tool.started`、`tool.completed`，临时目录当规则目录。
- 外壳：HTTP handler 用 httptest；路由矩阵。
- 前端：状态映射是纯函数（`src/lib/rule-state.ts`），照 `tests/` 现有写法。

**sdk 的用例**（4 条）：按 id 移除，大小写与空格不敏感，未持有的 id 不算错；改写是先移除再追加；按名字移除只改配置、`Reload` 才生效；移除后同名可以再加回来。

**积木的用例**（16 条，带 `-race` 跑过）：没配目录时是空操作；没有引擎时照常加载并回报；扫描器和积木放进同一个扩展集能一起加载；扫描调用从开始到完成被记账，被拒的调用不记账；加载时应用目录并写出节点文件；下一次调用读引擎之前生效；有扫描在跑时等它结束；空闲节点在一个检查间隔内应用；坏文件带原因，修好后应用；改写的 POC 就地替换；删除的文件离开引擎，放回来又加载；实例 POC 覆盖内置，删除后内置回来；实例指纹同样；改写被拒时上一版继续运行，两种规则都是；空库也写状态文件；新增的指纹和写了 `finger` 的 POC 被 `scan` 流水线自己的选择函数选中并命中，没写 `finger` 的不被选。

**证明测试**（6 条）：新增 POC 进入下一次选择和重建后的索引；`RemovePocs` 把模板拿出下一次选择；新增指纹在 `Reload` 后命中；同名改写后只剩一条、旧规则不再命中；`AddPocs` 只追加；gogo 在重载后的下一次扫描里报出新指纹。

**外壳的用例**：库的 17 条；handler 的 8 条；环境变量只留一份定义；路由矩阵、agent 面与层级表。

**门禁**（最终树）：引擎 `make check-fork` 没有超预算的钩子，也没有未登记的改动；外壳 `make gate GATE_ARGS=-skip-pg` 14 步全过，`internal/store` 的 PostgreSQL 契约测试带着测试库单独跑通过。不带 `-skip-pg` 时门禁停在第 4 步的 `TestProjectImportHandlerServerForm`（`cmd/zrcin`）：它只在设了 `ZRCIN_TEST_PG_DSN` 时运行，在基线 `7b1c87a` 上同样失败（二次导入一个已打开的项目，处理器里「目录已存在」的 500 分支排在「已打开」的 409 前面）。那是项目导入自己的问题，本方案没有改它。

**真实进程验证**（隔离实例，车道代码编出的 `zrcin`，独立端口与临时数据目录）：

- 空库启动就有状态文件，节点回报内置指纹 4,314 条、POC 83 条。
- 新增一条 POC，2 秒内变为已生效。
- 改写这条 POC（同 `id`），变为已生效，不再需要重启。
- 用实例 POC 覆盖一条内置 POC，已生效。
- 新增一条指纹和一条写了 `finger` 的 POC，都已生效。
- 删除两条 POC，记录消失。
- 把一条 POC 和一条指纹改坏，状态变为失败，原因里注明节点仍在运行上一版；删掉它们，记录清空。
- 节点的进程号始终没变。
- 页面上「覆盖内置」标记、POC 详情里的指纹绑定提示、新建模板里的 `finger` 字段都核对过。

**验证中修掉的缺陷**：空库不写状态文件；筛选值 `all` 被当成来源导致列表为空；`make web` 的 `WEB_DIR` 只生效一半；一处测试按原样比较指纹名，把匹配成功误判成失败（事实 19）。

**没做的**：键盘路径只做了代码层面的检查，没有逐键走一遍；1024 和 768 两档没有截图。窄屏下详情面板排在列表后面，要先滚过列表才看得到，和原来的页面一样。

## 10. 风险与回滚

| 风险 | 应对 |
| --- | --- |
| 增改引擎与匹配并发是数据竞争 | 空闲判定；用例带 `-race` |
| 签名漏掉同一时刻、同样大小的覆盖 | 写入方保证修改时间严格递增 |
| 积木要求借到引擎集，借不到会让节点加载失败 | 钩子在引擎初始化失败时给空集；用例覆盖「引擎为空，节点照常启动」 |
| 内嵌产物和前端源码对不上 | `make web` 现在把同一个检出交给构建和生成器 |

回滚：去掉装配里那一行，积木不加载，节点回到启动时加载一次；规则目录留着不影响任何东西。外壳与前端各自独立回退。4zgears 的两个方法是纯新增，可以留着。
